# 方向、零位、初始姿态与限位对齐

换机器人、重装电机/灵巧手、重新标定、修改驱动或模型后读本文件。默认服务器仍是 `192.168.8.30:2222`，SSH绑定接口 `wlo1`；配置在 `assets/server_profile.json`。`assets/profiles/new_robot_192_168_2_27/` 只是另一台机器的独立历史快照，不自动切换，也不自动覆盖默认标定。

## 先分清坐标和单位

|层|数值含义|配置/实现|
|---|---|---|
|电机编码器|原始电机位置，手部为电机弧度，可有±2π分支|驱动反馈、手部 `calibration.yaml`|
|逻辑关节|控制接口接受的解剖关节角度；回放包双臂/颈部用弧度，双手用度|HDF5、具名关节、`hand_io.HandCalibration`|
|仿真关节|URDF/MJCF坐标，包含轴方向和模型偏置|`configs/{arm,neck,hand}_mapping.json`|
|动作参考姿态|动作首尾采用的逻辑角度；通常不是0°|`configs/*_motion_defaults.json`、包内冻结的参考|
|起栈/界面/回放交接|启动、归零、回初始姿态、起播接近和结束归位分别选择的目标|服务器启动脚本、前后端和播放器|

生成器设计JSON统一输入逻辑关节**度数**，导出时仅将双臂/颈部转成弧度。手部已经是标定关节角时，不能再次套用电机换算。目标指令说明希望到哪里，实测反馈说明实际在哪里；用目标代替反馈会掩盖失联、滞后和校准问题。

## 方向要逐层核对，不能靠名字或左右正负猜测

1. 保存机器人身份、左右USB序列号、关节名→电机ID、驱动方向/偏置、双手四份YAML的字节哈希。先读**运行中的进程实际加载路径和参数**，不能只看磁盘上某个同名文件；YAML上传后，旧进程可能仍缓存旧标定。
2. 明确逻辑正方向的物理含义，例如“颈部J1增加时朝机器人自身哪一侧转”“J2增加时抬头还是低头”。查看URDF父子链、joint axis和FK。掌心朝向、拇指层级以几何和轴为准，不能仅凭MCP/ABD名字推断。
3. 在已有真机运动授权范围内，用远离接触/限位的单关节小增量（可从1–3°起）检查：原实测、目标、到达后的新鲜实测、实体运动方向、仿真运动方向。一次只动一个关节，记录观察视角是机器人自身左右还是观察者左右。没有运动授权则先做离线核对，真实方向标为待验证，不宣称已经对齐。
4. 分别确认“逻辑→电机”和“逻辑→模型”，同一反向补偿只能应用一次。保持逻辑接口不变时，换机导致的电机安装反向优先由该机驱动边界处理；模型映射保持逻辑语义一致。不要同时反转驱动、模型sign和包内角度。不能只反转下发而不核对反馈逆变换；速度、限位和零偏同样要检查。
5. 左右手臂数值镜像不等于实体对称。用掌部位置、法向、肘部方向和多视角图判断；左右灵巧手的ID、拉线方向和标定分别保存，不互相复制。

模型映射公式是：`q_model_rad = sign * q_logical_rad + offset_rad`。速度为 `v_model = sign * v_logical`。这里的 `sign` **不是电机驱动sign**。

例如当前默认颈部模型映射为J1 `sign=-1, offset=0.015rad`，J2 `sign=+1, offset=0.081rad`。因此逻辑 `[0,0]` 在模型中的qpos是 `[0.015,0.081]rad`，直接把MJCF qpos写成零会呈现另一姿态。另一台 `192.168.2.27` 保存的驱动配置方向为 `[+1,-1]`，其中只J2相对原配置反向；这是该机实例，不能作为默认机器的驱动参数。该profile的历史 `neck_driver_readback.json` 同时记录了尚未重启的旧进程参数，说明磁盘配置与运行值当时仍可能不同；不能把文件校验通过当作运行参数已经生效。

## 零位如何对齐

**手臂和颈部：** 在已知模型零姿态下记录真机的逻辑角 `q_zero_reading`，得到 `offset=-sign*q_zero_reading`。标定逻辑零、模型qpos零和机械安装中立位不一定重合。当前映射附有来源读数，但未独立验证的实体零位仍须标为未验证。改变baselink离地高度改变世界位置，不会修正电机零偏；改变网格原点也不能代替关节标定。

**灵巧手：** `config.yaml` 提供具名关节ROM、neutral_position以及关节到电机的正负ID；`calibration.yaml` 提供电机编码器端点及 `joint_to_motor_ratios`。编码器端点不是关节度数上下限。按内置真实换算类 `assets/robot/unified_ui/app/hand_io.py` 计算，不能取电机上下限的平均数当0°：

```
正常方向：q_deg = q_min + (motor_rad - wrap_rad - motor_min_rad) / ratio
反向电机：q_deg = q_max - (motor_rad - wrap_rad - motor_min_rad) / ratio
```

`ratio` 为电机弧度/关节度；使用标定文件中的比例，并核对 `motor_range == ratio * joint_ROM`。`neutral_position` 是配置的中立目标，不自动等于逻辑0°、模型0°或用户认可的初始手型。读取实时编码器要沿用驱动选择的±2π分支，不能每帧随意重选；校验范围时在标定文件自身的展开分支检查，实际下发再使用驱动当前分支。

校准后在相同实体手型下读数可能变化，应同步四份文件、确认运行进程重新加载、读取用户认可姿态的稳定实测，然后按 [手部参考生命周期](hand-reference.md) 建立新参考。`CalibratedHandPose.encoder_zero()` 计算逻辑0°对应的编码器位置，随后再通过模型sign/offset显示；这只证明数学换算，不证明网格与实体拉线安装已经测量对齐。

## 初始姿态和运行时目标要一致

动作首尾默认读取当前配置，并把参考ID、完整角度和标定哈希冻结进包。更新默认不会自动更新已生成动作，也不会修改真机。

- 颈部新动作首尾为逻辑 `[0°,0°]`。手臂为当前认可的对称抬手基准；手部为用户认可且验证过的参考手型，不强制归零。
- 当前颈部生成入口读取 `neck_motion_defaults.json`。历史 `motion_baseline.json` 或 `arm_motion_defaults.json` 内嵌的旧neck字段只作为历史记录保留，不是当前颈部目标；不能把它们合并覆盖独立的颈部默认。
- 起栈目标、界面“归零”（全0°）和“回初始姿态”（参考值）是独立功能，分别核对。启动顺序保持手臂到初始位后才启动/使能双手并到认可手型。
- 起播从**新鲜实测位置**平滑接近第一帧，历史约定1秒，差距较大或限速要求时延长；不在动作里插入先回旧基准的弯路。
- 结束时检查播放器的恢复/归位目标。曾出现包已回零，播放器随后又送 `[4.5°,-8.3°]` 的情况。本技能的本地播放器快照现已将颈部正常结束归位改为 `[0,0]`；这不意味着默认真机当前进程已修改。实际部署时读取该机实现并复核，单改包末帧无效。
- 未参与链保持空指令流。仿真对这些链的假设姿态写进元数据；实体若不处于假设姿态，组合碰撞结论不能直接沿用。

## 限位从哪里来，如何执行

|约束|来源|处理|
|---|---|---|
|双臂/颈部逻辑范围|映射 `real_limits_rad`，当前为有来源哈希的历史URDF数值快照|这是当前设计范围，不是对实体机械止挡的独立测量|
|手部逻辑ROM|左右 `config.yaml` 的 `joint_roms`|与hand_mapping的逻辑范围逐项一致；不同则导入失败|
|手部电机范围|各自 `calibration.yaml` 的 `motor_limits`、方向与ratio|逐帧逻辑角→编码器→关节往返校验，在标定展开分支检查编码器范围|
|仿真范围|映射 `model_limits_rad`、活动URDF和MJCF `jnt_range`|`model_limits=sorted(sign*real_limits+offset)`，负方向时上下限必须交换|
|速度和任务范围|设计的 `speed_caps_deg_s` 及具体任务约束|对最终密集轨迹检查，限速必要时延长时间，不能只验证关键帧|
|碰撞间隙|分块凸碰撞代理、已举证的装配规则和完整路径检查|与角度限位分开执行；在限位内仍可能碰撞|

实际可用范围取这些约束在同一坐标下的**交集**，再保留任务需要的余量。真机驱动的软硬限位须在该机另行核对；不能因URDF允许就认为真实拉线/电机也允许。当前默认速度上限是手臂25°/s、近头部15°/s、颈部15°/s、手指20°/s。某批PPT曾授权更高速度，不把该批的50/24/40°/s当成全局默认。

普通标定导入不改变ROM/轴/拓扑；发生这些变化时停止沿用旧模型，建立新资源版本并同步重建URDF、MJCF、映射、碰撞代理和来源证据。不要从已经加过偏置的模型范围反推新逻辑范围，否则会重复偏置。

生成全局五次样条可能在关键点之间过冲。检查的是完整导出时间轴、所有参与链、真实插值路径，不是只看首尾和设计点。离散命令之间的线性插值不会越过关节端点范围，但仍须查中间碰撞；速度按时间戳计算，加速后重查。当前代码报告加速度，未声称验证真机力矩/拉线负荷。碰撞失败先改姿态、路径或幅度，不扩大ROM、不裁剪关节造成折角、不降全局间隙凑通过。

## 每次换机/校准后的交付记录

运行离线数值核对（不连接服务器、不发指令）：

```bash
python scripts/alignment_audit.py --out work/verification/alignment.json
```

报告列出50个映射关节的逻辑/模型范围、sign/offset、模型零对应读数、动作参考，以及32个手部关节的电机ID/方向/比例/逻辑零编码器值和配置哈希。`numerical_checks_passed` 只表示本地数据一致，实体方向/零位仍按证据状态单独记录。

实际迁移记录至少包含机器人身份、驱动实际值和加载路径、YAML哈希、逐关节小增量观察、零位测量、原始/采用参考及最小修正、限位来源、起栈/起播/结束目标和所用模型版本。新机器仅保存一个profile并不等于已激活；手动选定连接目标后，还要完成标定导入、参考采用、方向零位核对和动作重新检查。未完成项明确写待验证，不复用另一台机器的“通过”。
